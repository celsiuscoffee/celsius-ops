# Loop engineering — end-to-end QA sweep

_2026-08-15. Scope: every engineered closed loop in the estate. Method: for each
loop, verify all four arms actually close — **trigger → action → measurement →
feedback** — against live `celsius-ops` prod data, then confirm suspected
defects in code rather than inferring them._

A loop that fires and acts but never measures is a broadcast, not a loop. A loop
that measures but never changes its own behaviour is a report. Both were checked
for explicitly.

## Verdict

The **marketing loop engine and the ads autopilot are genuinely closed loops** —
both were caught changing their own behaviour on evidence during the audit
window, which is the strongest possible pass. The real failures are concentrated
in the loops whose final arm is a **human** (reviews) or an **external
scheduler** (the warehouse routine), plus one genuine engineering defect in the
GBP scanner.

> healthy and the empty tables are dead schema I judged from row counts without
> checking which tables the code writes to. P1's *cause* was also wrong: it is
> Places API rate-limiting, not a per-outlet fault. Read those two sections in

## Findings, ranked

### P1 — The GBP geogrid loop burns half its monthly budget on failures, and Shah Alam has no rank data at all

The loop is capped at `GEOGRID_MONTHLY_SCAN_CAP = 40` scans/month, spent
worst-ranking-first. Two months running, the spend breaks down identically:

| Run | complete | partial | **failed** |
| --- | --- | --- | --- |
| 2026-08-03 | 13 | 7 | **20** |
| 2026-07-06 | 13 | 7 | **20** |

A `failed` scan means **all 81 grid points errored** (`scan-runner.ts:71`:
`failures === points.length`). It produces no rank, but it still writes a
`GeoGridScan` row — and the budget gate counts rows, not successes:

```ts
const scansThisMonth = await prisma.geoGridScan.count({ where: { createdAt: { gte: monthStart } } });
let budget = MONTHLY_CAP - scansThisMonth;
if (budget <= 0) return NextResponse.json({ capped: true, ... });
```

So failures consume the cap, and the loop cannot retry them until the next
month. Three consequences, all confirmed in the data:

1. **Shah Alam produced zero usable rank data.** All 8 of its Aug 3 combos
   failed — `cafe`, `cafes near me`, `best coffee near me`, `cafe seksyen 7`,
   `cafe seksyen 13`, `setia alam cafe`, `kopitiam near me`, `dessert near me`,
   `restaurants`. The busiest outlet is invisible to the ranking loop.
2. **IOI Mall has never been auto-scanned** despite 16 active keywords, and
   Putrajaya had no scans at all in August (last was a manual scan Jul 21) —
   the cap ran out before the sort reached them.
3. **The weekly adaptive cadence is defeated.** The whole month's budget is
   spent on the first Monday, so Aug 10 (and Jul 13/20/27) returned
   `capped: true`. The design intent — "working combos ~weekly, at-goal combos
   ~monthly" — cannot happen under a cap that empties on day one.

**FIXED.** Three changes, all in `cron/geogrid-scan` + `lib/geogrid/scan-runner`:

1. The monthly cap now counts only scans that returned data
   (`status <> 'failed'`), both when reading the month's spend and when
   decrementing in-run. Failures no longer buy out the budget.
2. Because failures are now free, a new `MAX_ATTEMPTS_PER_RUN` (default 60,
   above the 40 cap so a healthy run is never clipped) bounds attempts — "free"
   must not become unbounded Places API spend when an outlet is wholly broken.
3. The due queue is round-robined across outlets by `interleaveByOutlet`, so the
   neediest outlet still leads but can no longer consume the whole run before
   the others are reached. This is what starved IOI Mall and Putrajaya.

The response now reports `attempts`, `failed`, `errored` and
`attemptCeilingHit` separately, so a run can't report "scanned 40" while half of
them came back empty. Pinned by `scan-runner.test.ts`.

**ROOT CAUSE FOUND — and it was not what this report first said.** The earlier
guess ("a per-outlet cause — a bad `placeId`/coords or a keyed API restriction")
is **withdrawn**. Shah Alam's `placeId` (`ChIJFcHSHJlNzDERtGh5CheG0XE`) and
coords (3.0733, 101.5185) are both fine, and the failures are not confined to
it: on Aug 3, Tamarind failed 7 and Nilai 4 as well.

Ordering the Aug 3 run by `createdAt` shows what actually happened:

| seq | outlet | status | note |
| --- | --- | --- | --- |
| 1–7 | Tamarind | complete | ~4–5s each |
| 8–9 | Tamarind | partial | |
| 10–14 | Tamarind | **failed** | ~1–2s each — too fast to have called anything |
| 15–20 | Nilai | partial/failed | |
| **21–26** | Nilai | **complete** | **recovers** |
| 27–31 | Nilai/Tamarind | partial → failed | |
| 32–40 | Shah Alam | **failed** | all 9, run ends here |

**A scan that recovers mid-run is not a broken outlet — it is a rate limit.**
`scanGrid` fires 8 concurrent Places calls per batch with no throttle, no retry
and no backoff; the cron then chains ~40 of those back to back, so one run is
~3,240 calls as fast as the network allows. Google starts rejecting, the failed
points return in ~1–2s instead of ~4–5s, and nothing retries them. Shah Alam
reads as 100% broken purely because it sits **last** in the queue, by which
point the limiter is saturated and the run ends before it can recover.

**Fixed:** retry with exponential backoff + jitter on the retryable statuses
(429, 5xx, and network errors with no status) — a rate limit becomes a pause
instead of a lost scan, and the backoff is what paces the burst. Non-retryable
statuses (400/401/403/404 — bad key, denial, bad request) still fail fast, since
retrying those only wastes quota. A `PlacesApiError` now carries the HTTP status
so the two can be told apart, and the first failure reason is surfaced per scan
as `why` in the cron response — **a failed scan previously recorded nothing about
why, which is what let a rate limit masquerade as a broken outlet for two
months.** A `RUN_DEADLINE_MS` guard (240s, under the 300s `maxDuration`) stops
new scans starting once retries have stretched a run, so the function is never
killed mid-scan.

**Separately, IOI Mall's cause is different and now handled.** Its
`reviewSettings.gbpLocationName` is NULL, so `runScan` threw
"Outlet has no GBP location connected" on every attempt — it was never a
budget-starvation victim as first reported, it simply cannot scan. Outlets with
no GBP location are now filtered out before the queue is built (so they stop
burning an attempt per keyword) and reported once as `skippedNoGbpLocation`.
**Connecting IOI Mall's Google profile is an owner action** — 16 active keywords
are waiting on it.

### P2 — The reviews loop nudges on arrival but never on ageing — HALF FIXED

31 reply drafts have ever been created; **28 are still `pending`**, the oldest
from 2026-06-24 and the newest 2026-08-09. One was resolved, two rejected, and
**zero recovery codes have ever been issued or claimed** — so the recovery arm,
which is the point of the loop, has never once fired.

**The mechanism is a cadence gap, not a missing nudge.** `ops-nudge-review` runs
every 5 minutes, ingests new negative reviews into `ReviewReplyDraft`, DMs the
on-shift team and digests the managers — all of that works. But `recordBreach`
dedupes per review, deliberately, so **each review is nudged exactly once, on
arrival.** A draft nobody actions in those first minutes is never mentioned
again. Nudging on arrival is right for guest recovery; the missing half was
nudging on *ageing*.

**Fixed:** `runReviewBacklogNudge()` re-surfaces pending drafts older than
`REVIEW_DRAFT_STALE_DAYS` (default 3) as a manager digest led by the oldest —
"28 waiting" reads as backlog, "oldest 52 days" reads as a guest nobody
answered. It fires **once a day**: the route already runs every 5 min via the
dispatcher, so gating on a single 5-minute window (10:00 MYT) gives exactly one
digest and costs no new cron slot. Respects `OPS_NUDGES_MODE` like every other
nudge.

**Deliberately NOT done: arming auto-reply for negative reviews.** This report
originally floated that as the alternative. It should not be taken lightly, and
certainly not by an agent: replying to 1–3★ reviews is **already a documented
design decision, not an oversight.** `reviews-auto-reply/route.ts` states
negatives "are intentionally NOT touched here — they are never generated or
posted… they stay on the human-approval path until the risk-classifier work
lands. This is the zero-risk wedge." Arming it would post brand replies to
unhappy customers on a public Google profile — outward-facing, hard to retract,
and against a written stance. **Owner's call, and it wants the risk-classifier
first.** The backlog digest closes the visibility gap without touching it.

### P4 — The fleet heartbeat is incomplete, so "stopped" and "quiet" look identical — FIXED

Ten `armed` agents have `last_run_at = NULL` in `agent_registry` while several
are demonstrably logging actions. `/agents` therefore cannot tell a
healthy-but-quiet loop from a dead one — the same gap the `loops-trigger` route
already fixed for `sms_lifecycle_loops` and `round_gap_loop`.

**The mechanism is not simply "nobody called `touchAgentRun`".** For the finance
agents the call exists — it is on the wrong route.
`/api/cron/ap-match-apply` and `/api/cron/gl-post` both heartbeat correctly, but
**neither is scheduled**; the scheduled `bukku-feed-sync` imports
`applyApMatches` and `postBankLinesToGl` directly and never touched the
registry. Same shape for `agent_comms_digest`, whose only real caller is the
fold inside `celsius-overview`. The heartbeat has to sit on the path that
actually runs, which is why the fix targets callers rather than routes.

Fixed for nine, each on its live path:

| Agent | Heartbeat added in |
| --- | --- |
| `finance_ap_agent`, `finance_ap_match_apply`, `finance_gl_post` | `cron/bukku-feed-sync` (the scheduled driver) |
| `agent_comms_digest` | `ai-agent/celsius-overview` (the 13:00 UTC fold) |
| `marketing_strategist`, `ops_intelligence`, `procurement_advisor` | each agent's own `run*()`, after the mode gate |
| `data_analyst` | `answerDataQuestion()` |
| `hr_ops_agent` | `handleStaffInbound()`, after the mode gate |

In every case the stamp sits **before** the quiet-exit paths — no reorder point,
no campaign outcomes, no API key — because a quiet run is exactly what needs to
be distinguishable from a stopped one.

The tenth, `pos_pairing_tuner`, has no TypeScript path at all: pg_cron calls
`public.refresh_pos_pairing_signals()` directly. Its heartbeat ships as
`packages/db/prisma/migrations/20260815_pos_pairing_tuner_heartbeat/` —
**written and syntax-checked against prod but deliberately NOT applied**, since
prod DB changes are human-in-the-loop (hard rule 6).

This compounds the standing "most Vercel crons have no heartbeat monitoring"
item in STATE — it is the reason P3 and P6 went unnoticed.

### P5 — Latent: the kill rule will silently start judging on partial evidence

`loop-engine.ts:1482` (`autoPauseUnderperformers`) and `:1704`
(`getEvaluation`) both do an unbounded select over **all** measured rounds:

```ts
.from("loop_rounds").select("loop_key, stats").eq("status", "measured");
```

This is the repo's known PostgREST 1000-row truncation class (STATE, 2026-08-03:
_"any unbounded `.select()` … is a latent truncation bug"_). Currently 344
measured rounds, growing ~7/day — it crosses 1,000 around **November 2026**,
after which the pause/kill decisions and the evaluation dashboard silently read
a subset. Fix with the existing `fetchAllRows` helper
(`apps/backoffice/src/lib/hr/fetch-all.ts`).

## Lessons

- **A quiet loop is not a broken loop.** Four marketing loops looked dead; all
  four were deliberate pauses with recorded reasons, one of them the engine's
  own kill rule. Check the pause ledger before reporting a stoppage.
- **Status literals matter when reading health tables.** `ads_sync_log.status`
  is `OK`, not `success` — filtering on the wrong literal made 7 healthy nightly
  syncs read as 7 failures.
- **The loops that fail are the ones whose last arm leaves the system.** Every
  fully-automated loop here is healthy; the broken ones hand off to a human (P2)
  or an external scheduler (P6). This held up even after P3 was withdrawn — it
  was the one "broken" loop that turned out not to leave the system at all.
- **Row counts are not a pipeline.** P3 was called starved because three tables
  held zero rows. Two of them have no code writing to them at all, and the third
  belongs to a manual upload screen; the actual pipeline runs on
  `BankStatementLine` (59k rows) and was healthy throughout. **Before calling a
  loop starved, find the writer** — an empty table proves nothing about the loop
  that was supposed to fill it, only about the table.
- **Check whether "broken" is actually a documented decision.** The negative-
  review queue looked like an unclosed loop; the code says in plain words that
  negatives are held for human approval on purpose. A design stance written in a
  comment is still a design stance.
- **"Which outlet fails" is a distribution, not a diagnosis.** Shah Alam's 100%
  failure rate read as a per-outlet fault and was reported as one. Ordering the
  same rows by time instead of grouping them by outlet showed scans *recovering*
  mid-run — which no per-outlet fault can do — and turned it into a rate limit.
  When a failure looks entity-specific, sort by time before believing it.
- **A failure that records no reason will be misdiagnosed.** The geogrid loop
  stored `status='failed'` and nothing else, so two months of daily evidence
  could not distinguish a throttled API from a broken profile. Any loop that can
  fail should persist *why*, not just *that*.
