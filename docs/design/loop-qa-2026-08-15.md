# Loop engineering — end-to-end QA sweep

_2026-08-15. Scope: every engineered closed loop in the estate. Method: for each
loop, verify all four arms actually close — **trigger → action → measurement →
feedback** — against live `celsius-ops` prod data, then confirm suspected
defects in code rather than inferring them._

A loop that fires and acts but never measures is a broadcast, not a loop. A loop
that measures but never changes its own behaviour is a report. Both were checked
for explicitly.

## Verdict

The **marketing loop engine and the ads autopilot are genuinely closed loops** —
both were caught changing their own behaviour on evidence during the audit
window, which is the strongest possible pass. The failures are concentrated in
the loops whose final arm is a **human** (reviews) or an **external input**
(finance AP, GBP scans).

## What is working (verified, not assumed)

**Marketing loop engine — the feedback arm demonstrably fires.**
7 loops run daily (`winback`, `welcome`, `birthday`, `reward_expiring`, `habit`,
`aov_push`, `lapsed_deep`). 432 rounds, 344 measured, **0 past their attribution
window** — `autoMeasureDueRounds` is keeping up. 19,694 assignments, 1,219
conversions, 264 redemptions.

The kill rule is not decorative: **`fresh_lapse` auto-paused itself on
2026-08-13** — _"+0.2pp lift, RM-2.16/recipient margin after 1296 sends (holdout
102) — can't cover its own SMS"_. Three of the ten loop keys are paused
(`beans_idle`, `fresh_lapse`, both `round_gap` arms), each with a recorded
reason. What looked at first like four dead loops was the engine working.

Two design details verified as correct rather than taken on trust:
- Holdout contamination is excluded — a holdout treated by a sibling loop inside
  the window is dropped from the baseline, with the count kept as an audit trail.
- Money units are right: `total` is cents in **both** `orders` (avg RM32.90) and
  `pos_orders` (avg RM27.89), so the `/100` in `measureRound` is correct.
- The kill rule prices sends at SMS cost; push is only ~1% of sends (182 of
  ~17.6k), so that assumption holds today.

**Ads autopilot.** All 5 nightly sync kinds `OK` 10/10 over 10 days. The budget
ledger shows continuous evidence-led action: Putrajaya step-down Aug 12, Shah
Alam rollback Aug 12, Tamarind pause-probe Aug 3. Tamarind is `status=3` (paused)
at RM46.32 — the probe is in flight and on schedule for its ~Aug 17 verdict.

**Cron topology.** Backoffice sits at **38/40** Vercel cron slots. The 40-slot
cap silently drops extras, so this is worth watching — it is guarded by
`vercel-crons.test.ts`, and the `ops-nudges` and `procurement-loop` dispatchers
correctly fold 6 and 2 sub-jobs into single slots. Of 20 cron routes not listed
in `vercel.json`, **all 20 are reachable** via a dispatcher, another cron, a lib
caller or the admin UI — no orphaned schedules.

## Findings, ranked

### P1 — The GBP geogrid loop burns half its monthly budget on failures, and Shah Alam has no rank data at all

The loop is capped at `GEOGRID_MONTHLY_SCAN_CAP = 40` scans/month, spent
worst-ranking-first. Two months running, the spend breaks down identically:

| Run | complete | partial | **failed** |
| --- | --- | --- | --- |
| 2026-08-03 | 13 | 7 | **20** |
| 2026-07-06 | 13 | 7 | **20** |

A `failed` scan means **all 81 grid points errored** (`scan-runner.ts:71`:
`failures === points.length`). It produces no rank, but it still writes a
`GeoGridScan` row — and the budget gate counts rows, not successes:

```ts
const scansThisMonth = await prisma.geoGridScan.count({ where: { createdAt: { gte: monthStart } } });
let budget = MONTHLY_CAP - scansThisMonth;
if (budget <= 0) return NextResponse.json({ capped: true, ... });
```

So failures consume the cap, and the loop cannot retry them until the next
month. Three consequences, all confirmed in the data:

1. **Shah Alam produced zero usable rank data.** All 8 of its Aug 3 combos
   failed — `cafe`, `cafes near me`, `best coffee near me`, `cafe seksyen 7`,
   `cafe seksyen 13`, `setia alam cafe`, `kopitiam near me`, `dessert near me`,
   `restaurants`. The busiest outlet is invisible to the ranking loop.
2. **IOI Mall has never been auto-scanned** despite 16 active keywords, and
   Putrajaya had no scans at all in August (last was a manual scan Jul 21) —
   the cap ran out before the sort reached them.
3. **The weekly adaptive cadence is defeated.** The whole month's budget is
   spent on the first Monday, so Aug 10 (and Jul 13/20/27) returned
   `capped: true`. The design intent — "working combos ~weekly, at-goal combos
   ~monthly" — cannot happen under a cap that empties on day one.

**FIXED.** Three changes, all in `cron/geogrid-scan` + `lib/geogrid/scan-runner`:

1. The monthly cap now counts only scans that returned data
   (`status <> 'failed'`), both when reading the month's spend and when
   decrementing in-run. Failures no longer buy out the budget.
2. Because failures are now free, a new `MAX_ATTEMPTS_PER_RUN` (default 60,
   above the 40 cap so a healthy run is never clipped) bounds attempts — "free"
   must not become unbounded Places API spend when an outlet is wholly broken.
3. The due queue is round-robined across outlets by `interleaveByOutlet`, so the
   neediest outlet still leads but can no longer consume the whole run before
   the others are reached. This is what starved IOI Mall and Putrajaya.

The response now reports `attempts`, `failed`, `errored` and
`attemptCeilingHit` separately, so a run can't report "scanned 40" while half of
them came back empty. Pinned by `scan-runner.test.ts`.

**Still owner's call:** the 100%-failure signature on Shah Alam looks like a
per-outlet cause — a bad `placeId`/coords or a keyed API restriction — not
random flake. The fix above stops it starving the other outlets, but it will not
make Shah Alam scan; that needs one manual scan to diagnose.

### P2 — The reviews recovery loop's human arm has never closed

31 reply drafts have ever been created; **28 are still `pending`**, the oldest
from June. Only 1 was ever resolved and 2 rejected. `reviews_auto_reply` is
armed and working (82 actions in 30d), but `reviews_negative_drafts` is in
`shadow` mode — it drafts, a human is supposed to send, and nobody does. The
loop generates work indefinitely and nothing consumes it. Either staff the
review step, or arm the agent for the low-risk reply classes.

### P3 — The finance AP / bank-reconciliation arm is armed but has never had an input

`fin_bank_transactions`, `fin_bills` and `fin_exceptions` all hold **zero rows,
ever** — while `finance_ap_agent`, `finance_ap_match_apply` and
`finance_gl_post` are all registered `armed`, and `bukku-feed-sync` runs 4×/day
carrying `applyApMatches` and `postBankLinesToGl`. The daily EOD → GL half is
healthy (`fin_transactions` 5,553 rows, `fin_journal_lines` 12,731, both fresh
yesterday), so this is specifically the bank/AP feed. The exception inbox that
the finance-module spec treats as the loop's control surface has never received
an item. Most likely the Bukku feed was never connected — worth confirming
whether that is intended during the Bukku retirement, because three armed agents
are currently no-ops.

### P4 — The fleet heartbeat is incomplete, so "stopped" and "quiet" look identical — FIXED

Ten `armed` agents have `last_run_at = NULL` in `agent_registry` while several
are demonstrably logging actions. `/agents` therefore cannot tell a
healthy-but-quiet loop from a dead one — the same gap the `loops-trigger` route
already fixed for `sms_lifecycle_loops` and `round_gap_loop`.

**The mechanism is not simply "nobody called `touchAgentRun`".** For the finance
agents the call exists — it is on the wrong route.
`/api/cron/ap-match-apply` and `/api/cron/gl-post` both heartbeat correctly, but
**neither is scheduled**; the scheduled `bukku-feed-sync` imports
`applyApMatches` and `postBankLinesToGl` directly and never touched the
registry. Same shape for `agent_comms_digest`, whose only real caller is the
fold inside `celsius-overview`. The heartbeat has to sit on the path that
actually runs, which is why the fix targets callers rather than routes.

Fixed for nine, each on its live path:

| Agent | Heartbeat added in |
| --- | --- |
| `finance_ap_agent`, `finance_ap_match_apply`, `finance_gl_post` | `cron/bukku-feed-sync` (the scheduled driver) |
| `agent_comms_digest` | `ai-agent/celsius-overview` (the 13:00 UTC fold) |
| `marketing_strategist`, `ops_intelligence`, `procurement_advisor` | each agent's own `run*()`, after the mode gate |
| `data_analyst` | `answerDataQuestion()` |
| `hr_ops_agent` | `handleStaffInbound()`, after the mode gate |

In every case the stamp sits **before** the quiet-exit paths — no reorder point,
no campaign outcomes, no API key — because a quiet run is exactly what needs to
be distinguishable from a stopped one.

The tenth, `pos_pairing_tuner`, has no TypeScript path at all: pg_cron calls
`public.refresh_pos_pairing_signals()` directly. Its heartbeat ships as
`packages/db/prisma/migrations/20260815_pos_pairing_tuner_heartbeat/` —
**written and syntax-checked against prod but deliberately NOT applied**, since
prod DB changes are human-in-the-loop (hard rule 6).

This compounds the standing "most Vercel crons have no heartbeat monitoring"
item in STATE — it is the reason P3 and P6 went unnoticed.

### P5 — Latent: the kill rule will silently start judging on partial evidence

`loop-engine.ts:1482` (`autoPauseUnderperformers`) and `:1704`
(`getEvaluation`) both do an unbounded select over **all** measured rounds:

```ts
.from("loop_rounds").select("loop_key, stats").eq("status", "measured");
```

This is the repo's known PostgREST 1000-row truncation class (STATE, 2026-08-03:
_"any unbounded `.select()` … is a latent truncation bug"_). Currently 344
measured rounds, growing ~7/day — it crosses 1,000 around **November 2026**,
after which the pause/kill decisions and the evaluation dashboard silently read
a subset. Fix with the existing `fetchAllRows` helper
(`apps/backoffice/src/lib/hr/fetch-all.ts`).

### P6 — `finance_warehouse` has been stopped for three weeks

Last run **2026-07-24** (~512h). It is a scheduled *task* (an agent routine), not
a Vercel cron, so nothing in the repo will restart it — it needs the routine
re-armed. In `shadow` mode, so nothing downstream broke, but the warehouse
custodian checks (freshness/integrity across the estate) have not run since,
which is also why the dead Nilai `consignment_sales` feed noted in STATE went
another three weeks unflagged.

### P7 — Latent: attribution windows open before the message is sent

`measureRound` opens each member's window at `assigned_at` (prepare time), but
scheduled rounds send later — 14 rounds carry a gap of up to **8.03h** across 796
assignments. Orders in that gap would count as conversions the SMS could not
have caused. **Checked: zero such conversions exist to date**, because the
affected rounds are all lapsed-segment winbacks whose members rarely order.
Latent only — but the correct anchor is `sent_at`, and the fix also restores the
full post-send observation window that is currently truncated by the same gap.

### P8 — The three known ads defects, all confirmed live in code

STATE lists these as queued cleanup. All three verified present; the first is
now deleted.

1. **`hardCutDirective` was stale — DELETED.** It cut any listed campaign above
   RM55 back to RM55 whenever the till read healthy.

   Its own comment said to remove it once all three campaigns landed, which they
   did on 2026-07-20. The reason it could not just be left alone is that **it
   never self-expired the way it read**: the guard was
   `dailyBudgetMyr <= HARD_CUT_TARGET_MYR → null`, which holds only while the
   budget *stays* under RM55 and re-arms the moment one rises back above. It was
   not a spent directive sitting harmlessly — it was primed to fire again on the
   next raise, and the next raise due is **Shah Alam's probe-up when its rollback
   hold ends ~Oct 7**, which it would have chopped straight back to RM55.

   Deleting it changes nothing today: all three sit below RM55 (SA 53.98,
   Putrajaya 38.16, Tamarind 46.32 paused), so it was already dormant. Nothing
   replaces it — the guarded descent, rollback and pause-probe already own budget
   movement and read the till rather than a fixed number. Two tests replace the
   three that covered it: an above-RM55 campaign is no longer chopped to RM55,
   and a raised campaign is judged identically whether or not its name is on the
   old list.

2. **Probe verdicts trigger on raw-OR-adjusted** (`autopilot.ts:393`:
   `p.index < GUARD_RAW_MIN || (p.adjIndex != null && p.adjIndex < GUARD_ADJ_MIN)`).
   The payday/MoM safeguards that protect the normal path don't apply here, so
   the probe can call a verdict off the raw index alone. **Still open, and
   deliberately so** — the Tamarind probe is mid-flight and its verdict is due
   ~Aug 17. Changing the verdict rule under a running experiment is how you get
   a result nobody can interpret. Fix it after the verdict lands.
3. **`organic-revenue.ts` still has no `source <> 'grabfood'` filter** on its
   `pos_orders` branch (~line 50). Worth ~0.02 on the index — it strips
   reward/promo/voucher orders but not marketplace ones. **Still open, same
   reasoning:** it moves the very index the probe is being judged on.

### P9 — `ops-reminders` is a no-op consumer

`OpsReminder` has **zero rows, ever**, yet the sweep runs hourly. The cron is
correct — it only re-pings existing open reminders, and none have ever been
created. A working feature nobody uses: a candidate for the housekeeping utility
audit's decision memo, not a bug.

## Lessons

- **A quiet loop is not a broken loop.** Four marketing loops looked dead; all
  four were deliberate pauses with recorded reasons, one of them the engine's
  own kill rule. Check the pause ledger before reporting a stoppage.
- **Status literals matter when reading health tables.** `ads_sync_log.status`
  is `OK`, not `success` — filtering on the wrong literal made 7 healthy nightly
  syncs read as 7 failures.
- **The loops that fail are the ones whose last arm leaves the system.** Every
  fully-automated loop here is healthy; every broken one hands off to a human
  (P2), an external feed (P3), or an external scheduler (P6).
